## Разделить агента и судью (сменные ACP/протокольные адаптеры)

Цель: иметь возможность заменить адаптер Kiro на другой или подключить
второй клиент, чтобы агент (тот, кто делает работу) и судья (тот, кто
оценивает) были разными моделями/обёртками.

Контекст: два разных смысла слова "судья"

- Детерминированный оценщик (`eval/measure.js`, `verify_candidate`) — не
  ИИ, гоняет `explain()` и считает числа. Уже развязан, ACP не касается.
- LLM-as-judge — отдельная модель, оценивающая работу первой. Вот ради
  него и нужна поддержка второго клиента.

Что сейчас мешает

- `runner.py` создаёт клиента сам внутри `__init__` и жёстко привязан к
  классу `KiroAcpClient`. Клиент ровно один на прогон, места под судью нет.
- `KiroAcpClient` заточен под ACP-диалект Kiro (команда `kiro-cli acp`,
  движки v2/v3, методы `session/*`). Codex говорит по другому протоколу
  (app-server), Claude Code родного ACP не имеет — подключается через
  сторонний ACP-мост. Значит другой агент — это другой клиент, не флаг.

План (снизу вверх)

- Шаг 1. Ввести интерфейс клиента. Раннер реально использует только
  `start()`, `prompt(text)`, `close()`. Объявить протокол из этих трёх
  методов, раннер зависит от абстракции, `KiroAcpClient` — одна из
  реализаций.
- Шаг 2. Не создавать клиента внутри раннера, а передавать снаружи
  (инъекция зависимости). Разблокирует и замену агента, и двух клиентов в
  одном прогоне. Затрагивает `runner.py`, немного `main.py`/`chain.py`.
- Шаг 3. Развести роли "агент" и "судья". Точка расширения уже есть:
  `verify_candidate` / `ground_decision`. Сделать вариант задачи, где
  источник объективного `result.json` — второй клиент (LLM-судья), а не
  только Node-оценщик.

Заметки и риски

- LLM-судья недетерминирован — его вердикт приземлять в числа осторожно
  или комбинировать с детерминированными метриками, иначе теряется смысл
  "объективного" слоя.
- Клиент под Codex — самая большая часть (отдельный протокол app-server,
  на проводе даже опускают `"jsonrpc":"2.0"`).
- Клиент под Claude Code — проще через готовый ACP-мост, близко к текущему
  `KiroAcpClient`, но другая команда запуска и без v2/v3-специфики.
- Новые протокольные клиенты добавлять последними, по одному, каждый как
  отдельную реализацию интерфейса, не трогая раннер.
