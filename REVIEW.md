# Обзор проекта `agentic-workflow-sdk` (agentflow)

Дата анализа: 2026-09-29
Автор анализа: Claude (по запросу владельца репозитория)

## Что это

Async-first Python-библиотека для построения агентных workflow'ов в стиле
LangGraph: типизированный State с редьюсерами по каналам, граф узлов/рёбер с
условной маршрутизацией, суперстеп-движок исполнения, durable-чекпоинтинг и
человек-в-цикле (HITL) через `interrupt`/`resume`. Поддерживает два класса
бэкендов за одним событийным протоколом — агентные CLI-сессии (Kiro, Codex,
Claude Code) и стейтлес LLM (Ollama, любой OpenAI-совместимый эндпоинт,
Anthropic Messages API). Ядро (`agentflow/`) — 4211 строк, без внешних
зависимостей; офлайн-тесты — 2444 строки, 92 теста, все зелёные
(`pytest -q` → `92 passed, 8 deselected`).

Проект — недавний целевой rewrite (см. коммит `935511b`) более раннего
«mongo-optimization orchestrator»; история коммитов показывает 20 итераций
с последовательным наращиванием возможностей (input-валидация, all-or-nothing
суперстепы, run timeout, subgraph-as-node, HITL, resilience-обёртки,
Anthropic/OpenAI бэкенды, телеметрия) — это не черновик, а доведённая до
рабочего состояния система.

## Сильные стороны

1. **Чистая слоистая архитектура.** `state.py` (чистые данные) →
   `graph.py`/`runtime.py`/`compiled.py` (движок, backend-agnostic) →
   `backends/` (протоколы `Backend`/`AgentBackend`/`LLMBackend`) →
   `checkpoint/`, `telemetry.py`, `observability.py` (ортогональные сервисы).
   Зависимости идут строго в одну сторону; `agentflow` (без бэкендов)
   не тянет ни `subprocess`, ни HTTP-клиентов — это явно проверено
   в CI (`py.typed` + сборка колеса).

2. **Корректная модель суперстепов.** Bulk-synchronous parallel исполнение
   (как в LangGraph/Pregel): фронтир узлов идёт параллельно
   (`asyncio.gather`), обновления сворачиваются через редьюсеры в
   детерминированном порядке, шаг **all-or-nothing** — при ошибке любого
   узла обновления шага отбрасываются целиком и чекпоинт не пишется
   (`runtime.py:263-266`). Это сильная, продуманная гарантия согласованности.

3. **Durable checkpointing и HITL как основа, а не надстройка.** Каждый
   суперстеп чекпоинтится; `FileCheckpointer` пишет атомарно
   (temp-файл + `os.replace`), валидирует thread id от path traversal
   (`checkpoint/file.py:33-36`). `ctx.interrupt()` + `app.resume(thread, value=...)`
   работают через персистентный фронтир — прерывание переживает рестарт
   процесса. Реализация `Interactive`-политики разрешений через
   `contextvars.ContextVar` (`current_context`), чтобы permission-запрос
   backend'а мог достучаться до `ctx.interrupt` без явного проброса —
   изящное и хорошо задокументированное решение.

4. **Единый событийный протокол для агентов и LLM.** Общий `Backend`
   протокол с двумя специализациями (`AgentBackend`/`LLMBackend`) и общий
   словарь событий (`TextChunk`, `ToolCall`, `ToolResult`, `PermissionRequest`,
   `TurnEnd`, `BackendError`) позволяет узлу графа обращаться к Kiro, Codex,
   Claude Code, Ollama, OpenAI-совместимому или Anthropic API одинаково.
   `tool_loop` prebuilt честно реализует function-calling loop на уровне
   графа (LLM не выполняет тулы сама — это делает узел) — принципиально
   верная граница ответственности.

5. **Безопасность субпроцессов.** Все агентные бэкенды используют
   `asyncio.create_subprocess_exec` со списком аргументов (не `shell=True`),
   что исключает command injection. `ClaudeCodeBackend` явно скрабит
   `ANTHROPIC_*` переменные окружения дочернего процесса, чтобы CLI не
   унаследовал чужие ключи (`subprocess_env` hook) — внимание к деталям,
   которое легко упустить.

6. **Тестовая дисциплина.** Чёткое разделение офлайн/live тестов через
   pytest-маркер `live` (`addopts = -m 'not live'`), офлайн-сьют полностью
   мокает транспорт и гоняется в CI на 3.11/3.12, live-сьют бьёт по
   реальным CLI/Ollama/OpenAI/Anthropic и самостоятельно скипается при
   отсутствии бэкенда. Отдельные тесты на конкурентность, атомарность шага,
   timeout, HITL, subgraph, input-валидацию — это тесты именно инвариантов
   системы, а не только happy-path.

7. **Документация уровня инженерного контракта.** `DESIGN.md` — это
   pre-implementation RFC с явными non-goals, а не пост-фактум описание;
   `README.md` синхронизирован с реальным API (проверено чтением кода).
   Комментарии в коде объясняют «почему», а не «что» (напр. обоснование
   `contextvars`, обоснование atomic write, обоснование увеличенного
   read-buffer для ACP).

8. **Гигиена репозитория.** `.env` с реальными ключами корректно
   гитигнорится (проверено — не в индексе), в репозитории нет утёкших
   секретов, `dist/`, `telemetry/`, `.runs/` тоже не трекаются.

## Слабые стороны и риски

1. **Отсутствует файл LICENSE.** `pyproject.toml` заявляет
   `license = "MIT"`, но `LICENSE`/`LICENSE.txt` в корне нет. Для
   дистрибутива, который в `TODO`/README явно готовится к `pip install`,
   это блокер для внешнего использования — многие организации и PyPI-индексы
   такие пакеты трактуют как «без лицензии» = «все права защищены».

2. **Нет статического анализа в CI.** Ни `ruff`, ни `mypy`, ни `black` не
   установлены и не настроены (нет секций в `pyproject.toml`, инструменты
   отсутствуют даже локально в `.venv`). Код при этом активно использует
   тайпинг (`from __future__ import annotations`, `Annotated`, `Protocol`),
   но ничего не проверяет типы автоматически — расхождения типов будут
   ловиться только тестами или в рантайме.

3. **Нет retry/backoff на HTTP-бэкендах.** `OpenAIBackend`, `AnthropicBackend`,
   `OllamaBackend` не содержат обработки `429`/ретраев/backoff (проверено
   grep'ом — совпадений нет). Есть общий `with_retry`/`with_timeout` в
   `prebuilt/resilience.py`, но это обёртка над *узлом*, а не над HTTP-вызовом
   внутри бэкенда — то есть пользователю нужно не забыть обернуть каждый
   LLM-узел вручную; голый rate-limit от провайдера уронит `invoke()` сырым
   исключением.

4. **Только файловый/in-memory чекпоинтер.** Для продакшена (несколько
   процессов/масштабирование) нет `Checkpointer` поверх Redis/Postgres/SQLite;
   `FileCheckpointer` подходит для одной машины. Это осознанный `v1` выбор
   (см. non-goals — «no distributed execution»), но стоит явно обозначить
   как известное ограничение, а не только подразумевать.

5. **Evaluation-слой и OpenTelemetry — заявлены в `TODO.md`, но не начаты.**
   Для SDK, который позиционируется как production-grade agent framework,
   отсутствие батч-оценки (`evaluate(graph, dataset, evaluators)`) и
   OTel-экспортёра — заметный пробел против LangGraph/аналогов, где эти вещи
   уже есть «из коробки» или через экосистему.

6. **Нет измерения покрытия тестов.** `pytest-cov` не установлен, покрытие
   не считается ни локально, ни в CI — 92 прошедших теста не дают
   количественной гарантии, какая доля кода реально исполняется (особенно
   ветки ошибок в бэкендах, `BackendTransportError`-пути).

7. **Открытые `except Exception` в нескольких местах** (`observability.py:105`,
   `codebase_qa_ollama.py:221`, и т.п.) — осознанное решение (инструментация
   не должна ронять run), задокументировано, но такие широкие перехваты вне
   `hooks`-контекста (например, в примере с `_first_model()`) рискуют молча
   прятать настоящие ошибки конфигурации.

8. **Проектная гигиена контрибьютора отсутствует.** Нет `CONTRIBUTING.md`,
   `CHANGELOG.md`, issue/PR-шаблонов, `CODEOWNERS`. При одном авторе это не
   критично сейчас, но затрудняет онбординг, если проект начнёт принимать
   внешние вклады или публиковаться на PyPI.

9. **Версии зависимостей не зафиксированы.** `httpx>=0.27` без верхней
   границы и без lock-файла (`uv.lock`/`poetry.lock`) — для либы это
   нормально (не приложение), но CI-сборка не воспроизводима байт-в-байт
   между запусками при выходе новых минорных версий `httpx`.

10. **API ещё не стабилизирован по семантике версий.** Версия `0.1.0`,
    changelog отсутствует — потребителям пакета не на что ориентироваться
    насчёт breaking changes между версиями до релиза `1.0`.

## Чего не хватает (конкретные пробелы функциональности)

- Persistent-чекпоинтер для многопроцессного/распределённого запуска
  (Redis/Postgres/SQLite backend к протоколу `Checkpointer` — протокол уже
  абстрактный, реализовать новый класс дёшево).
- Встроенный retry/backoff и explicit rate-limit handling в LLM HTTP-бэкендах.
- `Evaluator`/batch-`evaluate()` слой (сам же `TODO.md` фиксирует это как
  следующий шаг).
- OpenTelemetry-экспортёр как ещё одна `Hooks`-реализация поверх уже готовой
  событийной модели (малая доработка учитывая архитектуру).
- Механизм ограничения параллелизма/конкурентности узлов в суперстепе
  (`asyncio.gather` на весь фронтир без семафора — при широком fan-out на
  внешний API это может быть неконтролируемым всплеском запросов).
- CLI/утилита для инспекции чекпоинтов (`agentflow inspect <thread>`) —
  осознанный non-goal v1, но по мере роста числа threads в `FileCheckpointer`
  будет не хватать хоть какой-то команды просмотра истории без Python REPL.
- LICENSE-файл, CHANGELOG, CONTRIBUTING — организационные артефакты перед
  публикацией пакета.

## Итоговая оценка

Это качественно спроектированная и добросовестно реализованная библиотека:
архитектурные решения (суперстепы, редьюсеры-каналы, единый backend-протокол,
чекпоинтинг с HITL) выверены и соответствуют модели LangGraph/Pregel,
код и документация синхронизированы, тесты покрывают именно инварианты
системы (атомарность, конкурентность, таймауты), а не только happy-path.
Основные риски лежат не в ядре движка, а на периферии эксплуатационной
готовности: отсутствие лицензии, статического анализа типов, устойчивости
HTTP-бэкендов к rate-limit'ам и production-грейд чекпоинтера. Для
внутреннего/экспериментального использования проект уже сейчас в отличном
состоянии; для публикации как открытого пакета или использования в проде
с реальным трафиком — нужно закрыть пункты из разделов выше, в первую
очередь LICENSE, ruff/mypy в CI и retry/backoff в HTTP-бэкендах.
