# Agent Workflow SDK — построение и исполнение workflow из запроса

Рабочие заметки по дизайну. Статус: **обсуждение, не реализация.** Ветка: `main` (не v2).

Документ фиксирует согласованные решения и открытые вопросы на момент последней
сессии обсуждения. Это не финальная спецификация — это протокол договорённостей.

---

## 0. Контекст и цель

Добавить в SDK встроенную возможность превращать запрос на естественном языке
в проверенный исполняемый workflow. Пользователь описывает задачу; система сама
проектирует граф и формирует реализацию шагов. **Пользователь не пишет функции узлов.**

Критерий готовности первой версии: один полный сценарий
`запрос → бриф → design/verify → утверждённый JSON-план → реализация →
компиляция → исполнение → проверенный результат`, где пользователь запускает
задачу без написания функций узлов, получает результат и может проследить,
как система построила и выполнила план. UI — следующий этап; в v1 достаточно
программного интерфейса или CLI.

---

## 1. Ключевой принцип: дженерик-движок, поведение в промптах

Самый важный тезис всего обсуждения.

- **Движок (код) домено-независим и пишется один раз.** Он не знает ни про
  Splunk, ни про Java, ни про какой-либо домен.
- **Поведение задаётся промптами и инвентарём**, а не кодом. Единственные
  «ручки настройки» системы:
  - промпты встроенных агентов проектирования и агентов исполнения;
  - содержимое инвентаря (доступные tools / skills / MCP / суб-агенты).
- Доменные сценарии (Splunk, «Java ниже 21») — это **не части системы**, а
  выходы, которые рождаются, когда дженерик-движок прогоняет конкретный промпт
  через конкретный инвентарь. Сменил промпт + инвентарь → другой домен, **без
  единой строки изменений в движке**.

Следствия-ограничения (дисциплина, нарушение = поломка «дженерик»):

1. Движок не имеет права знать про доменные типы шагов. Никаких
   `if step.type == "splunk_search"`. Нода для движка — всегда одно и то же:
   «вызови агента X через бэкенд со входами Y, тулами Z, прогони checks».
2. `checks` — тоже дженерик-механизм: движок исполняет *форму* проверки, не
   понимая домена. Какую проверку и с какими параметрами — решает дизайнер в плане.
3. `plan.json` — дженерик-контракт: доменно-нейтральные поля. Доменная
   специфика живёт в *значениях*, не в схеме.
4. Вариативность достигается только через промпты и инвентарь. Если для нового
   домена пришлось трогать код движка — принцип нарушен.

---

### Инвентарь и два уровня агентов

Система загружает определения доступных агентов, skills, MCP и tools из настроенных
директорий. Встроенные агенты проектирования получают каталог этих возможностей:

- `wf-orchestrator` формулирует бриф: цель, контекст и ограничения;
- `wf-creator` (Designer) создаёт JSON-граф, задания нод, ссылки на ресурсы,
  входы, выходы и проверки;
- `wf-verifier` оценивает логику плана относительно брифа и инвентаря и возвращает
  замечания создателю до утверждения и исполнения.

Агенты исполнения выбираются из инвентаря для нод готового графа. Их ролевые
промпты находятся в определениях агентов, а конкретный `prompt` каждой ноды
создаёт `wf-creator` и помещает в план. Специализированная роль на каждый шаг
не обязательна: одна роль может выполнять разные задания.

Неизвестная ссылка на ресурс — ошибка валидации. Автоматическое создание
недостающих агентов не согласовано; сборщик не создаёт их молча. Точные директории,
формат загрузки и фиксация версий инвентаря пока не определены.

## 2. Согласованная архитектура

```
запрос (NL)
   │
   ▼
┌──────────────────────────────────────────────┐
│ ТОЧКА 1 — ТВОРЧЕСТВО (агенты)                  │
│  wf-orchestrator → бриф                       │
│  wf-creator ⇄ wf-verifier (конечная петля)     │
│  • агенты знают инвентарь SDK                  │
│  • могут предлагать разные версии ПЛАНА        │
│  • verify проверяет ЛОГИКУ плана, не результаты│
└──────────────────────────────────────────────┘
   │
   ▼
[УТВЕРЖДЁН plan.json]  ─── единственная точка save/load
   │   • платформо-независимый контракт
   │   • ссылки на агентов/скиллы/mcp/тулы ПО ИМЕНИ
   │   • JSON-сериализуемый план задач (см. §2.1)
   ▼
┌──────────────────────────────────────────────┐
│ ТОЧКА 2 — ИСПОЛНЕНИЕ ПЛАНА КАК ДАННЫХ          │
│  план задач лежит в состоянии (by_key-канал)  │
│  add_plan_executor гоняет его по готовности    │
│  НЕ codegen; граф движка не мутируется         │
└──────────────────────────────────────────────┘
   │
   ▼
[валидация плана перед запуском]
   │   • все ссылки на ресурсы разрешимы в инвентаре
   │   • зависимости корректны, нет недопустимых циклов (DAG)
   │   • capability плана поддержаны выбранным бэкендом
   ▼
[исполнение через runtime SDK: add_plan_executor]
   │   • backend: kiro / claude / codex / raw LLM
   ▼
[проверка результатов — по содержанию, не «файл существует»]
```

> **Смена решения (проверено по коду движка).** Ранее здесь стоял
> «детерминированный рендер `plan.json → workflow.py`». Проверка исходников
> показала, что движок уже исполняет план как данные через
> `agentflow/prebuilt/plan_executor.py` (`add_plan_executor`): планировщик
> пишет граф задач `Task(id, kind, input, prerequisites)` в
> состояние (JSON-сериализуемый `by_key`-канал), а исполнитель гоняет задачи
> по готовности зависимостей, с параллельным fan-out и resume из `done_ids`.
> Это ровно то, к чему мы шли, но без кодогена. Последствия: codegen не нужен
> для исполнения; проблема «реестра воркеров» отпадает (один фиксированный
> граф, не регистрируемый на лету); проверка «граф изоморфен плану» становится
> ненужной (нечему расходиться — план И ЕСТЬ исполняемое). `workflow.py`
> остаётся ТОЛЬКО как опциональный читаемый артефакт для человека, не как путь
> исполнения.

### §2.1 Отображение `plan.json` на `plan_executor`

Наш шаг плана → `Task`:

| поле плана | поле `Task` |
|---|---|
| `id` | `Task.id` (стабильный, он же ключ дедупликации/идемпотентности) |
| вид шага (всегда один: «вызов агента») | `Task.kind = "agent_step"` |
| `agent`/`prompt`/`tools`/`inputs`/`checks`/… | `Task.input` (payload для обработчика) |
| `depends_on` | `Task.prerequisites` |

Один обработчик `kind="agent_step"`: разрешает входы, вызывает агента через
бэкенд, прогоняет `checks`, возвращает `TaskResult(output=...)` или
`TaskResult(failed=True, error=...)`. Упавшая задача считается *done*, но
блокирует зависимых — это встроенное поведение исполнителя, менять не нужно.

## 3. Твёрдо согласованные решения

1. **Две точки, две природы.**
   - Точка 1 (планирование) — агенты: творчество, вариативность, знание SDK.
   - Точка 2 (исполнение плана как данных) — `add_plan_executor`: план лежит
     в состоянии, исполнитель гоняет задачи по готовности зависимостей.
     Проектирование структуры и правил workflow завершается ДО утверждения
     плана; агенты выполняют задания уже при исполнении. НЕ codegen:
     граф движка фиксирован, новая задача — это данные, а не новый узел.
     Детерминирован отбор готовых задач и маршрутизация, НЕ ответы моделей.

2. **Граница «до исполнения» — жёсткая.** Вся петля design⇄verify работает только
   с планом, брифом и предоставленным инвентарём. Ноды workflow и их инструменты
   не запускаются, внешние источники задачи не опрашиваются. Вызовы самих агентов
   проектирования необходимы для этой петли. Верификатор проверяет *план*,
   а не *результаты*; доступность источников во время исполнения не подтверждается.

3. **Петля design⇄verify конечна и честна.** Ограничена числом итераций. При
   неснятых замечаниях за N проходов — терминальный стоп с явной причиной
   («остановлено на итерации N, неустранённые замечания: [...]»), НЕ проваливаемся
   в исполнение и не делаем вид, что план готов.

4. **Выход из петли — через утверждение; план получает версию.** Утверждение —
   отдельный шаг. Версия нужна, чтобы к ней привязалась реализация.

5. **`plan.json` — единственная точка save/load.** Сохраняется ТОЛЬКО утверждённый
   граф: после design, ДО материализации в код. Платформо-независимый контракт
   со ссылками (имена агентов/скиллов/mcp/тулов), а не встроенным кодом.
   Загрузил → продолжаешь с материализации. Черновики посреди петли — НЕ в v1.

6. **Исполнение — план как данные, не отдельный артефакт кода.**
   *(Пересмотрено — см. смену решения в §2.)* План задач исполняется напрямую
   через `add_plan_executor`; отдельный сгенерированный `workflow.py` НЕ нужен
   для исполнения. `workflow.py` допустим ТОЛЬКО как опциональный читаемый
   артефакт отладки для человека, и тогда он не путь исполнения. Это снимает
   проблему реестра воркеров и делает проверку «изоморфизм графа плану»
   ненужной. Крупные выходы шагов хранить в `Store`, а не в состоянии:
   чекпойнтер пишет состояние целиком на каждом шаге (см. §3 п.13).

7. **Совместимость бэкендов — НЕ реализуема сегодня, это работа над движком.**
   *(Уточнено по коду.)* Проверка показала: MCP/skills в бэкенды сейчас НЕ
   передаются — Kiro шлёт `mcpServers: []`, у claude_code/codex/anthropic/
   openai/ollama упоминаний MCP нет. Поэтому «передать агента/MCP/skills в
   бэкенд» требует доработки бэкендов + таблицы возможностей (OQ-9). В v1 агент
   выбирается ПО ИМЕНИ из инвентаря, а конкретное задание едет в тексте
   `prompt` ноды. План не привязан к Kiro. Проверка «план ↔ бэкенд умеет это» —
   в фазе валидации перед запуском, против каталога возможностей бэкендов.

8. **Три разные проверки, не путать.**
   - логика плана (Точка 1, до исполнения);
   - соответствие реализации плану (проверка сборки);
   - корректность результатов (после исполнения, по содержанию).

9. **Нода графа = один логический шаг исполнения.** Нода разрешает входы,
   формирует задание и вызывает выбранного агента через бэкенд. Внутри шага
   возможны повторные попытки и вызов агента проверки результата; число нод
   не равно числу вызовов бэкенда. Точный контракт передачи определения агента
   или выбора зарегистрированного агента по имени остаётся открытым (OQ-9).

10. **Проверка результата шага — двухслойная, оба слоя дженерик:**
    - детерминированные `checks` (код, без модели) — обязательный слой;
    - семантический вердикт агента-проверщика — когда объективной проверки мало.
    Модель НИКОГДА не управляет потоком сама: она производит результат и выдаёт
    суждение в структурированной форме, а поток управления решает код, читая
    структурированные результаты checks и вердикт (данные).
    Агент проверки результата получает задание, исходные данные, результат
    и критерий. Это роль исполнения, отличная от встроенного `wf-verifier`
    плана. Доступ к доказательствам исполнения ещё нужно определить (OQ-6).

11. **Цикл выполнить→проверить→повторить строится на `add_quality_gate`.**
    *(Привязано к коду.)* Шаг раскрывается в мини-граф `execute → gate(checks)
    → revise`, НЕ в «перезапуск ноды целиком» (при падении воркера перезапуск
    целиком теряет счётчик попыток и повторяет платные вызовы агента). Гейт даёт
    даром: попытки в состоянии (`gate_attempts`), три маршрута
    `on_pass/on_fail/on_escalate` (все обязательны → честный стоп гарантирован
    движком), `GateEvent(started→passed/failed/escalated, reasons)` для
    трассировки. `max_attempts` — лимит. Это ОТДЕЛЬНАЯ петля от design⇄verify.

12. **Повтор ноды — с обратной связью (вариант B).** Проверки возвращают не `false`,
    а структурированную причину отказа. Ложится на `GateResult.feedback` и
    `reasons`, которые идут в `revise`-узел и в следующую попытку, чтобы агент
    видел, что чинить. (Соответствует брифу: верификатор возвращает замечания.)

13. **Идемпотентность обязательна — контракт движка «at-least-once».**
    *(Добавлено по коду.)* Соседи по параллельному фронту перезапускаются при
    падении/прерывании → платные агентные вызовы повторяются. Шаги с побочными
    эффектами оборачивать `skip_if_done`/`IdempotentOp` с ключом из `task.id`
    (стабильный, переживает resume) + хеш разрешённых входов (`artifact_key`).
    Кешировать ЗНАЧЕНИЯ выходов, не дельты. В план ввести поле вроде
    `side_effects` / ключа идемпотентности для шагов с эффектами.

14. **Петля design⇄verify — тоже на `add_quality_gate`.**
    Форма: `creator → детерминированный валидатор → verifier-gate → creator`,
    с `max_attempts` и терминальным узлом «остановлено, замечания: [...]».
    Валидатор СТРОГО первым — чтобы не тратить вызовы верификатора на заведомо
    невалидные планы.

## 4. Цикл одной ноды при исполнении

```
┌─────────────────────────────────────────────┐
│  НОДА (одна попытка)                          │
│                                               │
│  1. выполнить: backend.invoke(агент, входы)   │  ← производство (модель)
│         ↓ результат                           │
│  2. детерминированные checks (код)            │  ← объективно: формат,
│         ↓ прошло?                             │     непустота, схема, exit code
│     ├─ нет ──► повтор(с причиной)? или стоп    │
│     └─ да ──►                                 │
│  3. semantic_check (проверщик результата)    │  ← по смыслу, если задано
│         ↓ вердикт как данные                  │
│     ├─ reject ──► повтор(с причиной)? или стоп │
│     └─ approve ─► нода завершена ✓            │
└─────────────────────────────────────────────┘
         │
         ▼ выход ноды → входы следующих нод
```

Обе петли реализуются через `add_quality_gate` (см. §3 п.11, п.14), а не
кодом «вручную»: попытки хранятся в состоянии, `on_escalate` даёт честный стоп,
`GateEvent` — трассировку. Шаг = мини-граф `execute → gate(checks) → revise`.

Две петли системы не путать:

| | уровень | когда | что проверяет | вызовы инструментов задачи? |
|---|---|---|---|---|
| design ⇄ verify | план | до исполнения | логику плана | нет |
| выполнить→проверить | нода | при исполнении | результат ноды | да |

## 5. Декларативные примитивы проверки (набор v1)

Принцип отбора: примитив входит в набор, только если он **доменно-нейтрален** и
**детерминированно исполним движком без модели**. Работает над выходом ноды или
произведённым артефактом. Движок проверяет форму и объём, не интерпретирует смысл.

**Группа 1 — существование и объём** (закрывает «файла недостаточно»)

| примитив | параметры | что проверяет |
|---|---|---|
| `not_empty` | target | выход/артефакт существует и непуст |
| `count` | target, min, max | число элементов в диапазоне |
| `size` | target, min, max | размер в байтах/символах в диапазоне |

**Группа 2 — структура**

| примитив | параметры | что проверяет |
|---|---|---|
| `matches_schema` | target, schema | соответствие JSON-схеме *(extra-зависимость)* |
| `has_fields` | target, fields[] | перечисленные поля присутствуют |
| `is_type` | target, type | тип значения (array/object/number/string) |

**Группа 3 — содержимое по образцу** (сопоставление, без понимания смысла)

| примитив | параметры | что проверяет |
|---|---|---|
| `matches_pattern` | target, regex | матч регулярного выражения *(лимит против ReDoS)* |
| `contains` | target, value | содержит подстроку/элемент |
| `in_set` | target, allowed[] | значение из допустимого множества |
| `value_range` | target, min, max | числовое значение в диапазоне |

**Группа 4 — внешняя объективная проверка**

| примитив | параметры | что проверяет |
|---|---|---|
| `command_succeeds` | argv[], allow, cwd, timeout, env | команда вернула exit 0 *(НЕ shell — см. ниже)* |
| `json_path` | target, path, op, value | значение по JSONPath *(extra-зависимость)* |

Итого **13 примитивов**. Стартовое ядро, намеренно маленькое.

### Безопасность примитивов (проверено по коду)

План пишет LLM, исполняется с инструментами — у примитивов есть поверхность атаки.

- **`command_succeeds` — только `argv[]`, никогда shell-строкой.** Проверка кода:
  `CommandWatcher` в движке идёт через `asyncio.create_subprocess_shell`, и по
  тому же пути пошёл бы текст от LLM → инъекция. Поэтому: массив `argv`, белый
  список допустимых исполняемых файлов (`allow`) в инвентаре, явный `cwd`,
  `timeout`, очищенное окружение `env`. Единственный примитив с реальным риском
  (OQ-2) — оставляем, но в такой форме.
- **`matches_pattern`:** regex приходит от модели → нужен лимит сложности/длины
  против ReDoS (катастрофический бэктрекинг).
- **`matches_schema` / `json_path`:** требуют `jsonschema` и JSONPath-библиотеки.
  Проверка кода: в ядре движка этих зависимостей НЕТ (инвариант «ядро без
  зависимостей»). → слой выпускать как extra (`agentflow[workflow]`) или
  отдельный пакет. «Тонкая прослойка» ровно так и стоит.
- **Агентам проектирования инструменты не нужны:** LLM-бэкенд без tools или
  `DenyAll`-политика.
- **У агентных бэкендов обязательна `PermissionPolicy`** — в плане её сейчас нет.
  Поле `tools` шага разумно отображать на `ToolAllowlist`. Но: реально во время
  хода политику применяет только Kiro; для Claude Code она превращается в
  `--allowed-tools`, для Codex — в режим песочницы.
### Доменные условия в параметрах примитивов и границы проверки

Домен живёт в *параметрах*, не в движке. Пример (расследование: временное окно,
поля фильтрации, пагинация) — иллюстрация проверки полей, не доказательство полноты:

```jsonc
"checks": [
  { "kind": "not_empty",  "target": "output.logs" },
  { "kind": "count",      "target": "output.logs", "min": 1 },
  { "kind": "has_fields", "target": "output.logs[*]",
                          "fields": ["timestamp", "service", "level"] },
  { "kind": "json_path",  "target": "output.pagination",
                          "path": "$.exhausted", "op": "eq", "value": true },
  { "kind": "json_path",  "target": "output.window",
                          "path": "$.from", "op": "exists" }
]
```

Движок видит только `not_empty / count / has_fields / json_path`. Он не знает, что
это логи, пагинация, временное окно. Домен целиком в `target`/`fields`/`path`,
которые положил дизайнер по своему промпту.

**Схема и значения полей не доказывают достоверность результата.** Проверка
`pagination.exhausted == true` подтверждает только значение поля. Для доказательства
полноты обхода нужны фактические ответы инструментов и проверка цепочки пагинации.
Наличие `source_url` не подтверждает происхождение ссылки, а наличие начала окна
не доказывает, что все запросы использовали одно и то же временное окно.

Непустота также не означает правильность. `not_empty` и `count.min = 1` допустимы
только там, где этого требует задача: пустая выборка может быть верным результатом.
Полноту, отсутствие пропусков и дубликатов, соответствие исходным записям требуется
проверять по исходным данным. Достаточность текущих примитивов для этого остаётся
открытой (OQ-3); способ сохранения доказательств и доступа к ним — OQ-6/OQ-7.

### Реализованные примитивы проверки

Исполняются шесть видов (`CHECKS` в `checks.py`, параметры в `CHECK_KEYS`): `not_empty`,
`has_fields`, `count` (`min`, `max`, `equals`, `same_count_as`), `compare` (`op`: `eq`, `ne`,
`gt`, `ge`, `lt`, `le`, `in`, `not_in`, `contains`, `starts_with`, `ends_with`, `exists`;
сравнивается с `value` или с другим полем `other`), `unique`, `sorted` (`key`, `order`).
`target` это выходное поле шага с необязательным путём: `items[*].level` (каждый элемент),
`items[0].name`, `meta.window.from`; отсутствие любой части пути это провал, а не пропуск.
Пустое совпадение по `[*]` тоже провал, пока не задан `allow_empty`. `true` не равно `1`,
`bool` не число. Параметры проверяет валидатор плана (`bad_check`: лишний или недостающий
ключ, неверный `op`, `target` вне выходов шага). Регулярных выражений нет намеренно:
шаблон приходит из плана, а у `re` нет таймаута (ReDoS). `command_succeeds` не
исполняется: подпроцесс из плана требует отдельного решения о безопасности.
Граница прежняя: эти проверки сравнивают ответ агента с самим собой и с константами
плана; факт о внешнем мире (файлы действительно такие) они не доказывают. Для этого
создатель добавляет независимый шаг-перепроверку, а полнота остаётся за человеком.

### Семантический уровень (второй дженерик-примитив проверки)

Для того, что структурно не выразить («эти данные действительно отвечают на вопрос»):

```jsonc
"semantic_check": {
  "agent": "verifier-agent",
  "criterion": "<промпт: что именно подтвердить по смыслу>"
}
```

Движок тут тоже дженерик: вызывает агента-проверщика с `criterion`, читает вердикт
как данные. Домен — в тексте `criterion`.

Нужна **схема вердикта** и политика на случай, когда вердикт не распарсился:
**стоп с причиной, а не approve** (нераспознанный вердикт ≠ «прошло»). Результаты
шага попадают в промпт проверщика **как данные, а не как инструкции** (защита от
того, что выход шага содержит текст вида «игнорируй проверку»).

### Структурированная причина отказа (для повтора с обратной связью)

Каждый примитив при провале возвращает не `false`, а причину:

```jsonc
{ "check": "has_fields", "passed": false,
  "reason": "missing field 'timestamp' in 3 of 120 elements" }
```

Форма дженерик, содержание конкретно. Причина идёт в следующую попытку ноды.

## 6. Структура `plan.json` (схема согласована; источник истины — файл JSON Schema при реализации)

```jsonc
{
  "schema_version": "1",          // версия ФОРМАТА; меняется только при несовместимых правках
  "plan_version": 1,              // версия самого плана-контракта
  "brief": { /* цель, контекст, ограничения, ожидаемые результаты, неоднозначности */ },
  "parameters": { "<имя>": "<тип>" },  // параметры запуска ($input.<имя>), см. §6.1
  "graph": {
    "steps": [
      {
        "id": "step_a",                   // = Task.id (стабильный, ключ идемпотентности)
        "agent": "<имя агента исполнения>", // ссылка на определение роли (по имени, v1)
        "prompt": "<конкретное задание, созданное wf-creator>",
        "permission": "read_only",         // read_only | allowlist | full (§6.2)
        "tools": [],                      // имена в словаре бэкенда; только при allowlist
        "skills": [], "mcp": [],          // зарезервировано: SDK не передаёт, валидатор
                                          // отвергает непустые значения (§3 п.7)
        "inputs": { /* привязки данных: закрытый набор видов, см. §6.1 */ },
        "outputs": { "<поле>": "<тип>" },  // контракт выхода; выше порога хранится ссылкой
                                          // {store_ref, size, sha256} (OQ-7)
        "artifacts": ["<имя артефакта>"],
        "side_effects": false,            // true -> IdempotentOp по ключу из task.id
        "may_ask": null,                  // или {"max_questions": 1, "default_answer": null} (OQ-11)
        "checks": [ /* дженерик-примитивы, см. §5 */ ],
        "semantic_check": { /* опционально: agent + criterion + схема вердикта */ },
        "budget": null,                   // опц.: лимит токенов на шаг
        "timeout": null,                  // опц.: таймаут шага (with_timeout)
        "max_attempts": 3,                // лимит петли gate ВНУТРИ шага
        "depends_on": []                  // = Task.prerequisites
      }
    ]
  },
  "final_outputs": [ { "step": "step_a", "field": "<поле из outputs>" } ],
  "run_limits": { "max_design_rounds": 3, "step_limit": null },
  "budget": null,                         // опц.: лимит токенов на весь план (BudgetState)
  "approval": { "mode": "manual", "status": "approved", "plan_hash": "...", "by": "...", "at": "..." },
  "verification": { "iterations": 2, "issues": [ /* формат замечания из OQ-5 */ ] },
  "provenance": { "inventory_digest": "<artifact_key снимка инвентаря>",
                  "engine_version": "<версия движка>", "plan_hash": "<artifact_key плана>" }
}
```

Замечания:
- каждый шаг напрямую отображается на `Task(id, kind="agent_step", input, prerequisites)`
  — см. §2.1; отдельный `workflow.py` для исполнения НЕ нужен;
- поля доменно-нейтральны; доменная специфика — только в значениях;
- `agent`/`skills`/`mcp`/`tools` — ссылки на ресурсы, не встроенный код; при
  валидации и `load` движок проверяет их разрешимость в предоставленном инвентаре;
- `prompt` задаёт работу ноды и не заменяет ролевой промпт определения агента;
- `command_succeeds`-проверки используют `argv[]` + allow-list, не shell (§5);
- `budget`/`timeout` опираются на существующие `BudgetState`/`with_timeout`;
- пример показывает состав полей; точные типы и допустимые значения фиксирует файл
  JSON Schema в репозитории, а `validate_plan` собирает проверки из спайков
  (`bindings_spike.py`, `capabilities_spike.py`) в одну функцию;
- валидатор сначала проверяет `schema_version` и отказывает понятной ошибкой на
  незнакомой, а не пытается разбирать;
- итог запуска: `completed` (все `final_outputs` получены), `partial` (часть получена,
  часть заблокирована), `failed` (ни одного итога); итог всегда содержит список
  заблокированных шагов и причин, молчаливого «успеха» с пустыми выходами нет;
- провал шага блокирует потомков, остальные ветки продолжаются (так работает
  `plan_executor`); повторы только внутри шага (`max_attempts`), повтор шага целиком
  на уровне плана в v1 не делается; `max_design_rounds` относится к проектированию.

### 6.1 Привязки данных между шагами (решено; OQ-8 закрыт в части входов)

Решение согласовано и проверено спайком `spikes/bindings_spike.py` (валидатор,
резолвер, рендер, сквозной прогон через `add_plan_executor`, обе реализации
чекпоинтера).

**Принцип: закрытый набор видов привязок, а не язык выражений.** Выражения писал
бы LLM: их нельзя заранее проверить валидатором, они ломают детерминизм и
открывают поверхность для инъекций. Расширяемость — добавлением нового вида в
реестр вместе со схемой и правилом валидации; неизвестный вид отвергается.

| Вид | Запись | Смысл |
|---|---|---|
| Ссылка на шаг | `{"from": "step.output.поле[.глубже]"}` | значение из результата шага |
| Параметр запуска | `{"from": "$input.имя"}` | значение, заданное при старте |
| Литерал | `{"value": ...}` | константа |
| Склейка | `{"from": [..], "combine": "concat" \| "merge"}` | объединить несколько источников |
| Артефакт | `{"artifact": "step.artifacts.имя"}` | передаётся ссылка (путь, ключ), не содержимое |

К любой привязке добавляются: `"then": [...]` — фиксированные чистые
преобразования (`first`, `len`, `unique`, `{"join": ","}`, `{"pick": "поле"}`),
`"type"` — ожидаемый тип, `"required": false` вместе с обязательным `"default"`.
Типы: `string`, `number`, `integer`, `boolean`, `array`, `object`, `any`. Пути в
v1 — точечные имена, не JSONPath (переход на JSONPath правил не меняет).

**Промпт статичен.** Шаблоны `{{ }}` не поддерживаются (`{"template": ...}` — это
ошибка валидации `unknown_binding_kind`). Динамика попадает к агенту только через
`inputs`: хендлер детерминированно дописывает после промпта блок
`### input: <имя>` + JSON, входы отсортированы по имени, ключи отсортированы;
одинаковые входы дают побайтово одинаковый текст. Превышение лимита размера —
ошибка с подсказкой передавать артефактом.

**Ссылаться можно на любого предка, не только на прямые зависимости.**
`plan_executor` запускает шаг лишь после успеха его предшественников, а те — после
своих, поэтому результат любого предка гарантированно есть. Валидатор доказывает
«это предок» статически (множество предков по `depends_on`). Это не усложняет
ключ кеша и не ослабляет гарантии. Асимметрия решения: ослабить строгий режим
можно без поломки планов, ужесточить мягкий нельзя; выбран мягкий осознанно.
Компенсация: валидатор строит граф потоков данных (кто что откуда берёт), и экран
утверждения показывает его рядом с графом зависимостей, помечая косвенные связи
(«через предка X»).

**Валидатор (детерминированный, без модели) возвращает ВСЕ ошибки с кодами:**
`duplicate_id`, `unknown_dependency`, `cycle`, `unknown_binding_kind`, `unknown_key`,
`unknown_step`, `not_ancestor`, `bad_path`, `unknown_output_field`, `unknown_param`,
`unknown_artifact`, `type_mismatch`, `bad_transform`, `bad_combine`,
`combine_needs_list`, `optional_needs_default`. Ссылка допустима только на поле,
объявленное в `outputs` шага-источника (шаг без объявленных `outputs` ни на что
не ссылается); статическая типизация грубая, всё глубже верхнего уровня и всё, что
не удалось типизировать, считается `any`.

**Во время исполнения:**
- нерешённая обязательная привязка **проваливает шаг с причиной**
  (`TaskResult(failed=True)`), агент не вызывается; исключение не бросается, иначе
  откатился бы весь параллельный раунд;
- объявленный контракт `outputs`/`artifacts` проверяется после ответа агента;
  нарушение проваливает шаг, зависимые не запускаются;
- значение проверяется на заявленный `type`; `first([])` означает «привязывать
  нечего» (нерешённая), а не исключение внутри преобразования.

**Ключ кеша шага** = `artifact_key({"agent", "prompt", "inputs": <разрешённые>})`.
Он зависит только от того, что агент реально увидит: изменение выхода upstream
меняет ключ у всех читающих его шагов, а изменение, которое шаг не читает, ключ
не трогает (в спайке: смена пути артефакта меняет ключ `report`, но не `enrich` и
`analyze`). Для полноты реального ключа стоит добавить `tools` шага и
`inventory_digest`.

**Не входит в v1 (точки расширения):** условное выполнение `when` (пропущенный
шаг даёт `{"skipped": true}`; привязка к возможно пропущенному предку обязана быть
опциональной, это правило должен проверять валидатор), размножение шага по списку
`foreach`, JSONPath, свои виды привязок.

### 6.2 Каталог возможностей бэкендов и права шага (решено; закрывает OQ-9 в части каталога)

Проверено по коду и экспериментами; спайк `spikes/capabilities_spike.py`.

**Каталог — обычная таблица в коде, не файл.** Валидатор плана сверяет шаг с
возможностями бэкенда, на котором он будет исполняться, и отвергает план, а не
подстраивается молча (в `agentflow` есть ловушка: `ToolAllowlist` на Codex молча
превращается в песочницу `read-only`, то есть строже, чем просили).

| Возможность | Kiro | Claude Code | Codex | LLM по HTTP (Ollama, OpenAI, Anthropic) |
|---|---|---|---|---|
| Как применяется политика | на лету, на каждый запрос разрешения | флагами при запуске | только песочница при запуске | по построению: исполняются лишь зарегистрированные `Tool` |
| Список разрешённых инструментов | да (`ToolAllowlist`) | да (`--allowed-tools`, имена Claude) | нет | да (набор `Tool`) |
| Только чтение | `DenyAll` | `--permission-mode plan` | `-s read-only` | инструменты не регистрируются |
| Полный доступ | `AllowAll` | `AllowAll` → `--permission-mode acceptEdits` (правки файлов; оболочка не открывается; не `bypassPermissions`) | `-s workspace-write` | все `Tool` |
| Агент по имени | да | да (`--agent`) | нет | нет |
| MCP через SDK | нет (`mcpServers: []` зашит) | только через `extra_args` | не проверено | нет |
| Skills через SDK | нет | нет | нет | нет |
| Эмитит `ToolResult` | да | **нет** (только `ToolCall`) | частично (только shell-команды) | неприменимо: инструменты исполняет граф |
| Сообщает `Usage` | нет | нет | да | только Ollama |
| Параллельные ходы на одном экземпляре | **нет**: `BackendError: a turn is already in progress` | запускается, но см. ниже | запускается, но см. ниже | да |
| Изоляция шагов | процесс/сессия на экземпляр | **экземпляр помнит последнюю сессию и возобновляет её** | то же | без состояния |

**Изоляция шагов (подтверждено экспериментом; частично решено в движке).**
`CLIExecBackend` хранит `_session_id` и подставляет его в следующий ход. Два
последовательных шага на одном экземпляре `CodexBackend` дали для второго
`resume th-1`: контекст первого шага протёк во второй. `invoke(..., session=None)`
откатывается к сохранённому. У Kiro параллельный ход на том же экземпляре просто
падает.

В движок добавлен **`reset_session()`** (async, на `BaseAgentBackend`): для
Codex и Claude Code забывает сохранённый id сессии, для Kiro открывает новую
ACP-сессию на том же процессе (с повторным применением режима агента или модели);
для бэкенда без состояния ничего не делает. Тест подтверждает: после сброса
следующий ход идёт без `resume`, а ход, начатый до сброса, не возвращает старую
сессию. Правила для исполнителя:
- **последовательные шаги** можно гнать на одном экземпляре, вызывая
  `reset_session()` между ними (для Kiro это дешевле нового процесса);
- **параллельные шаги** по-прежнему требуют отдельных экземпляров: у Kiro
  параллельный ход на одном экземпляре невозможен, у CLI-бэкендов параллельные
  ходы делили бы один `_session_id`; сброс во время хода Kiro даёт `BackendError`;
- предыдущая сессия Kiro по умолчанию остаётся нетронутой. **Проверено на настоящем
  kiro-cli 2.26:** процессу это ничего не стоит (RSS ~51 МБ и 62 дескриптора
  не растут за 12 сбросов, задержка сброса ~0,1 с), но каждая сессия хранится на
  диске (`~/.kiro/sessions/...`) и переживает закрытие процесса; `session/close`
  её из списка не убирает, `session/delete` убирает. Конвейер со сбросом на каждый
  шаг копит такие записи (10 сессий дали около 5,5 МБ вместе с логами). Для этого
  есть `reset_session(delete_previous=True)`: новая сессия создаётся первой (сбой
  создания оставляет старую целой), затем старая удаляется; история удалённой
  сессии пропадает, поэтому для разбора шага оставляйте значение по умолчанию.
  Агент заявляет `close`, `delete`, `list`, `fork` в `sessionCapabilities`;
- **поток событий Kiro можно оставить на `TurnEnd`**: ход считается завершённым в
  момент `TurnEnd`, и следующий `prompt()` или `reset_session()` сразу доступен
  (раньше они падали с «a turn is already in progress», пока генератор не
  финализировали). Выход из потока ДО `TurnEnd` по-прежнему оставляет ход активным.

**Поле `permission` шага** (по умолчанию самое строгое):

```jsonc
"permission": { "access": "read_only" | "allowlist" | "full", "tools": ["..."] }
```

- `read_only` — по умолчанию;
- `allowlist` — только перечисленные инструменты; имена **в словаре бэкенда**
  (у Claude Code свои имена), поэтому список привязан к бэкенду из инвентаря;
- `full` — только явно; экран утверждения показывает его отдельной пометкой.

**Правила сверки плана с каталогом (коды ошибок валидатора):**
`unknown_backend`, `backend_cannot_enforce` (например `allowlist` на Codex),
`backend_no_mcp` / `backend_no_skills` (шаг просит MCP или skills там, где SDK их
не передаёт), `backend_no_agent_by_name`, `evidence_unavailable` (шаг объявил
`requires_evidence: true`, а бэкенд не эмитит `ToolResult`: проверка по
доказательствам невозможна), `usage_unavailable` (на шаге задан токенный бюджет,
а бэкенд не сообщает `Usage`; нужна оценка по длине текста либо отказ от
токенного лимита). Все правила проверяются **до** запуска.

**Проверено на настоящих агентах** (`codex 0.163`, `claude 2.1.292`, `kiro-cli 2.26`; пустая папка, задача «создай `out.txt` с текстом `hi`», фиксировался факт записи файла):

| Политика | Codex | Claude Code | Kiro |
|---|---|---|---|
| `read_only` (`DenyAll`) | не записал | не записал (режим `plan`) | не записал |
| `allowlist` со словарём бэкенда | `{write, shell}` **не записал**: молча стал `read-only` | `{Write}` записал; `{Read}` не записал | `{fs_write}` записал; `{fs_read}` не записал |
| `full` (`AllowAll`) | записал (`workspace-write`) | **не записал**: агент вызвал `Write`, получил отказ | записал |
| `AllowAll` + `permission_mode="acceptEdits"` | не применимо | записал | не применимо |

Выводы: (1) ловушка Codex подтверждена, валидатор обязан отвергать `allowlist` для
Codex; (2) **для Claude Code `access: full` не работает по умолчанию**: в
неинтерактивном режиме без разрешающих флагов запись запрещена, то есть `AllowAll` на
нём действует как `read_only`. Чтобы шаг с `full` реально мог писать, нужно явно
задать `permission_mode` (проверен `acceptEdits`). Решено в бэкенде:
`AllowAll` на `ClaudeCodeBackend` теперь даёт `acceptEdits` (явные
`allowed_tools`/`permission_mode` по-прежнему главнее); режимы `bypassPermissions` и `skip_permissions` я не
запускал: автоматическая проверка безопасности запретила такой запуск, и обходить
её я не стал; (3) словарь инструментов Kiro в `PermissionRequest`: `fs_write`,
`fs_read`; у Claude Code свой (`Write`, `Read`).

**Брошенный ход Kiro до `TurnEnd` (проверено):** пока потребитель держит
генератор, агент **продолжает работу** (за 4 секунды 66 событий, 13,6 КБ), а наша
очередь событий растёт без ограничения; новый ход на том же экземпляре в это время
отклоняется («a turn is already in progress»). Когда генератор закрыт и начат новый
ход, агент сам отменяет прежний (stopReason `cancelled`), новый ход отвечает чисто
(текст предыдущего хода в нём не появился; гонку для не-текстовых событий этот тест
не исключает). Явный ACP `session/cancel` останавливает агента сразу (ответ
`cancelled` мгновенно, 6 хвостовых событий), следующий ход после него работает.
Вывод: брошенный ход тратит работу агента впустую; поэтому `KiroBackend` теперь
сам шлёт `session/cancel`, когда поток событий закрыт до `TurnEnd`.

**Два процесса Kiro одновременно (проверено):** два независимых `kiro-cli` в одном
workspace, по 6 сбросов с `delete_previous=True` и ходом каждый, одновременно:
ошибок нет, в списке остались ровно две живые сессии (из 14 созданных), каждый
процесс удалил только свои, обе живые сессии отвечают.

**Ограничения, которые остаются:** режимы Claude Code `bypassPermissions` и
`skip_permissions` не проверялись (запуск запрещён автоматической проверкой
безопасности); применение политики на лету есть только у Kiro, остальные бэкенды
ограничены на старте и дальше доверяются своей песочнице; проверен один тип
действия (запись файла) на одном маленьком задании. Загрузка каталога из файлов и
версионирование — вне v1 (OQ-10).

### Критерий полноты плана для механической сборки (OQ-5)

План готов к механической сборке, если сборщик не принимает новых решений
о поведении workflow: задания, ресурсы, входы, выходы, зависимости, проверки
и правила завершения однозначно определены планом и фиксированными правилами SDK.

Обязательные сведения (точные поля и их семантика ещё не утверждены):

- идентификатор, исполнитель и конкретное задание каждого шага;
- ссылки на необходимые ресурсы инвентаря;
- происхождение входов и контракт выходов;
- зависимости и условия запуска;
- проверки результата и ограниченные правила повторов и остановки;
- объявленные итоговые выходы workflow.

Разделение ответственности:

| Механизм | Ответственность |
|---|---|
| Детерминированный валидатор | Обязательные поля, уникальные ID, корректность ссылок и привязок, допустимые зависимости, разрешимость ресурсов, поддерживаемая форма проверок и правил исполнения |
| `wf-verifier` | Соответствие брифу, полнота действий, допущения, достаточность ресурсов и данных, способность предусмотренных проверок выявить неверный результат |
| Утверждение | Разрешение перехода к сборке; механизм выбирается отдельно в OQ-4 |

Связность графа сама по себе не обязательна: независимые ветки могут давать разные
требуемые результаты. Нужны корректные зависимости, отсутствие недопустимых циклов
и определённые итоговые выходы. Допустимые формы управления ещё уточняются.

**v1 — только DAG (из ревью).** Валидатор обязан проверять ацикличность
топосортом. Движок циклы допускает (единственная защита — `step_limit`), а
`plan_executor` при цикле между задачами просто пометит их как недостижимые
(`plan_stalled`). Условные переходы и циклы МЕЖДУ шагами в v1 не нужны:
единственный цикл — внутри шага (`execute → gate → revise`). Отказ от codegen
убирает условные переходы/циклы между шагами как возможность — это осознанный
размен, приемлемый для v1.

Одобрение `wf-verifier` означает отсутствие выявленных им логических недостатков,
а не доказательство правильности будущего результата. До исполнения проверяется,
предусмотрены ли действия и достаточные доказательства; фактические данные
проверяются при исполнении. Формальная валидация, семантическая проверка плана
и утверждение не заменяют друг друга. **OQ-5 частично уточнён, но не закрыт.**

## 6.3 Где живёт код и как он ставится (решено)

Слой «запрос -> план -> граф» входит в SDK как подпакет `agentflow.workflow`, а не как
отдельный пакет. Причины: слой не имеет сторонних зависимостей; он тесно связан с SDK
(каталог возможностей закреплён тестом на реальные классы бэкендов, `plan_hash` и
`inventory_digest` используют `artifact_key`, исполнитель строится на
`add_plan_executor`, `engine_version` пишется в план); один разработчик и одна машина,
поэтому выгоды независимых релизов нет; документ, спайки и CHANGELOG уже здесь.

Границы удерживаются проверками, а не репозиторием:
- движок не импортирует `agentflow.workflow` (тест `tests/workflow/test_isolation.py`);
- слой использует только стандартную библиотеку и `agentflow`;
- импорт явный (`from agentflow.workflow import validate_plan`), корневой
  `agentflow/__init__.py` слой не реэкспортирует;
- у слоя свой раздел в CHANGELOG.

Если позже слой понадобится выделить, подпакет с односторонней зависимостью
извлекается без переписывания.

**Статус реализации (`agentflow.workflow`).** Готово и покрыто тестами: схема и
валидатор плана, инвентарь, привязки данных, проверки утверждения, исполнитель
(`run_plan`: кеш результатов по ключу содержимого, шаг как gate-подграф на
детерминированном под-потоке, `IdempotentOp` для `side_effects`, итог
`completed | partial | failed`). Проверено мутациями: без кеша, без `IdempotentOp`,
без проверки утверждения, без учёта проверок в ключе кеша и без перехвата ошибки
бэкенда соответствующие тесты падают. Счётчик попыток переживает падение и
возобновление в самом исполнителе. Реализован и `may_ask` (по OQ-11, с одним
отличием от первоначального наброска: вопрос задаётся не отдельной задачей плана, а
внутри обработчика шага через `ctx.interrupt`; повтор после ответа безопасен, потому
что завершённая попытка читается из своего долговечного под-потока, а не запускается
заново): `ask_mode="stop"` останавливает шаг с `needs_clarification`,
`ask_mode="interrupt"` приостанавливает запуск (`RunOutcome.status == "waiting"`),
`default_answer` отвечает сам; ответ человека для нового запуска передаётся как
`answers={шаг: ответ}`. `resume_plan` продолжает ожидающий, удержанный или упавший
запуск после повторной проверки утверждения; с `inventory_source` утверждение
перепроверяется перед каждым шагом по ТЕКУЩЕМУ инвентарю, и отозванное утверждение
переводит запуск в `held`, а не в провал. Статусы запуска в коде:
`completed | partial | failed` для завершённого, `waiting` и `held` для
приостановленного. «Ожидает утверждения» (`awaiting_approval`) запуском не является:
неутверждённый план отклоняется до создания запуска (`PlanRefused`, код
`not_approved`). Фаза проектирования реализована (`design_plan`): оркестратор -> бриф,
создатель <-> проверки, ограниченный `max_rounds`. Детерминированные проверки
(`validate_plan`, `unsupported_features` и правило минимума доказательств: шаг без
проверок или только с `not_empty` возвращается создателю как `check_cannot_detect_failure`
кодом, без верификатора) идут ДО верификатора, поэтому невалидный план не стоит вызова
модели. Итог: `converged`, `round_limit` (решает человек, с неснятыми замечаниями),
`not_executable` (утвердить нельзя) или `failed`. Дизайнеры видят только имена, описания
и допустимые права агентов. `approve_plan` связывает утверждение с `plan_hash` и
`inventory_digest`; `try_auto_approve` утверждает без человека только при пройденном
пороге и без открытых `blocker`. Живая проверка проектирования (настоящий `claude` во всех трёх ролях без
инструментов, один агент `worker` в инвентаре, запрос «три самых длинных .txt в
каталоге»): создатель выдал валидный трёхшаговый план (подсчёт строк, отбор трёх, сводка),
план прошёл механические проверки и был утверждён и выполнен тем же слоем:
`completed`, верный ответ (200, 120 и 80 строк). При этом верификатор ставил `blocker`
`check_cannot_detect_failure` на шаг подсчёта: единственная доступная проверка
`has_fields` не ловит неверные числа, а более сильных примитивов у исполнителя пока
нет (только `not_empty` и `has_fields`), поэтому замечание нельзя было снять и цикл
закончился с открытыми замечаниями (человек решает). Вывод: набор примитивов проверки
(OQ-1, OQ-3) сейчас главное ограничение качества планов, а не проектирование. Номера
раундов и итоговый статус в этом прогоне не сохранены (вывод был обрезан), повторять
его не стали. Роли проектирования (`wf-orchestrator`, `wf-creator`, `wf-verifier`) существуют как
шаблоны промптов и, дополнительно, как готовые определения агентов. Формат у бэкендов
РАЗНЫЙ (по документации провайдеров): Claude Code читает Markdown с YAML-frontmatter из
`.claude/agents/`, Kiro читает JSON или Markdown из `.kiro/agents/`, у Codex пользовательские
агенты это TOML (`.codex/agents/`), но SDK не умеет выбрать такого агента по имени, поэтому
для Codex определение не генерируется и дизайнер получает полный промпт. Определения
генерируются из промптов (один источник), лежат в `agentflow/workflow/agent_files/` и
устанавливаются пользователем явной командой `python -m agentflow.workflow install` в
каталог, который он назвал; значения по умолчанию нет, различающийся файл не
перезаписывается без `--force`. Для Claude Code есть вариант без установки: `--agents` с
JSON на одну сессию (`claude_designer`). Живая проверка: на `kiro-cli` агент `wf-orchestrator`
из JSON во временном рабочем каталоге выбран и ответил брифом в нужном формате (доверие к
каталогу помехой не было); `claude` с инлайн-агентами (`--agents`, без установки,
`named_agents=True`) прошёл весь цикл: бриф, два раунда создатель/верификатор, итог
`round_limit` с открытыми `blocker` (`check_cannot_detect_failure`, `hidden_assumption`),
то есть работает так же, как с полным промптом; причина остановки прежняя: доступных
проверок недостаточно, чтобы снять замечания по доказательствам. Пока НЕ исполняется и поэтому отклоняется до запуска:
`semantic_check`, бюджеты, таймауты, артефакты, `may_ask` вместе с `side_effects`,
примитивы проверки вне набора ниже.
Повторный живой прогон после расширения набора: создатель сам использует `count`, `sorted`, `unique`,
`compare` и добавляет независимый шаг-перепроверку; блокеры `check_cannot_detect_failure` на
самих проверках ушли, цикл всё равно закончился `round_limit`, но по существу (пустой каталог
ломает `not_empty` на перепроверке, нет правила для равных счётчиков). Живая проверка: двухшаговый план (`read_only`, настоящий `claude` через
`backend_runner`) завершился как `completed`: данные первого шага («Paris») пришли
во второй через привязку, итог «PARIS», по одной попытке на шаг. `kiro-cli` и `codex`
через этот слой в живую не запускались: для них проверено только сопоставление
политики и класса бэкенда.

**Установка.** `pip install agent-workflow-sdk` кладёт пакет в `site-packages`
активного окружения; это обычная библиотека, она ничего не запускает и не создаёт
данных. Данные живут в рабочем каталоге проекта, который выбирает пользователь:
`inventory.json` и `.runs/<run_id>/` (OQ-7). Бэкенды (`claude`, `kiro-cli`, `codex`)
ставятся в систему отдельно, SDK только запускает их подпроцессами. Сервер для UI
(FastAPI на `127.0.0.1`) логично поставляется как extra (`[server]`), чтобы библиотека
не тянула лишнего. Утверждённый план привязан к `inventory_digest` и `engine_version`:
после обновления SDK формат чекпойнта может измениться, и такой запуск отклоняется с
понятной причиной (OQ-7).

## 7. Открытые вопросы

### Активные (нужны для завершения дизайна)

- **[OQ-1] Набор из 13 примитивов — ок как стартовое ядро v1?**
  Ревью: старт нормальный. Осталось решить, как адресуется артефакт-файл
  (не только JSON-выход шага) — язык адресации `target`.

- **[OQ-2] `command_succeeds` — форма зафиксирована.** Оставляем, но НЕ строкой:
  `argv[]` + белый список + cwd/timeout/чистое env (см. §5 «Безопасность»).
  Причина подтверждена кодом: `CommandWatcher` движка идёт через shell.

- **[OQ-3] Выразительность примитивов.** Подтверждена модель «два дженерик-уровня»
  (декларативный + семантический). Нужно ещё раз проверить на нескольких реальных
  задачах, что связки примитивов + семантика покрывают нужные проверки, включая
  полноту выборки, отсутствие пропусков/дубликатов и соответствие источникам.

- **[OQ-4] Механизм утверждения плана. РЕШЕНО.**
  - Режимы в конфигурации запуска: `approval: manual | auto`, по умолчанию `manual`.
    `manual` = `ctx.interrupt` с `QualityGateReview`. `auto` пропускает узел
    утверждения, но только для плана, прошедшего порог прав (ниже); иначе режим
    становится `manual` с указанием причины. Отдельный режим `policy` не нужен: это
    `auto` с порогом.
  - Порог для `auto` (все условия сразу): нет шагов с `permission: full`; нет команд
    вне белого списка; все бэкенды есть в каталоге; нет `may_ask` без
    `default_answer`. Проверяется кодом, не моделью.
  - Человеку показываются эффективные права, а не проза: по каждому шагу бэкенд,
    `permission`, инструменты, каждая команда как `argv` с cwd и белым списком,
    привязки данных, `inventory_digest`. Текст агента-проектировщика выводится
    отдельно и помечен как неподтверждённый.
  - Утверждается хэш плана (`artifact_key`). Если план изменился после утверждения
    (повторное проектирование, правка инвентаря), утверждение недействительно и
    запрашивается заново. Хэш пишется в состояние и в трассировку.
  - Исходы для человека: утвердить или отклонить с замечанием (замечание идёт в
    проектирование как обратная связь). Ручная правка плана не входит в v1: она
    требует заново прогнать валидатор и верификатор.
  - Без человека (`manual`, нет ответа): остановка с причиной `awaiting_approval`,
    молчаливого утверждения нет.
  - Принятая цена: автоутверждение узкое, большинство планов с записью файлов
    придётся утверждать вручную, пока нет опыта.

- **[OQ-5] Что именно гарантирует verifier в ПОЛНОМ плане. РЕШЕНО (контракт);
  списки кодов допишутся вместе с кодом валидатора.**
  - Три уровня с чёткой границей (таблица в §6): валидатор (код, бинарный результат:
    план собирается или нет), `wf-verifier` (модель: «замечаний нет» либо список
    замечаний), утверждение (OQ-4).
  - Валидатор проверяет: уникальность id, ацикличность (топосорт), разрешимость
    привязок (§6.1), права и совместимость с бэкендом (§6.2), поддерживаемую форму
    проверок, лимиты `may_ask` (OQ-11).
  - Замечание verifier структурировано: `{code, step_id|null, severity:
    blocker|warning, claim, evidence_needed}`, код из закрытого списка (например
    `brief_not_covered`, `check_cannot_detect_failure`, `hidden_assumption`), чтобы
    замечания можно было сравнивать между итерациями. `blocker` возвращает план в
    проектирование с замечаниями как обратной связью; `warning` показывается при
    утверждении и не блокирует.
  - Достаточность доказательств: для каждого шага verifier отвечает, какая проверка
    поймает неверный результат и на каком примере упала бы. Нет ответа =
    `check_cannot_detect_failure` (blocker). Минимум проверяется и кодом: у шага нет
    проверок вообще, или все проверки только `not_empty`.
  - Цикл «проектирование -> валидатор -> verifier» ограничен `max_design_rounds`
    (по умолчанию 3). После лимита план уходит человеку с неснятыми замечаниями:
    ни молчаливого принятия, ни бесконечного цикла.
  - Вне v1: условные переходы и циклы между шагами (только DAG); формат
    `final_outputs` идёт в OQ-8.
  - Честная оговорка: `wf-verifier` остаётся моделью, поэтому «замечаний нет» не
    доказательство корректности; это покрывается детерминированными проверками
    минимума выше и утверждением.

- **[OQ-6] Прослеживаемость (traceability). РЕШЕНО.** Хранилище не изобретаем:
  `JsonlTelemetry` + история чекпойнтов дают трейс, ПРИ УСЛОВИИ что нода делает
  `ctx.emit` на каждое событие бэкенда (проверено кодом: Kiro эмитит `ToolResult`;
  Codex только для shell-команд; `claude_code` импортирует только `ToolCall`).
  - Флаг `emits_tool_results` в каталоге (§6.2). Валидатор не принимает шаг, чья
    проверка опирается на доказательство по инструменту, на бэкенде без флага. Для
    таких бэкендов проверки строятся по артефакту на диске (`file_exists`,
    `has_fields`), а в отчёте шаг помечается «проверено по артефакту», не «по трассе».
  - `JsonlTelemetry` обрезает `text` до 500 символов: для трассы достаточно, полный
    вывод шага лежит в `Store`, в трассе ссылка (см. OQ-7).
  - Слой включает `Redactor` по умолчанию для трассы и сохранённых артефактов (в SDK
    редактор выключен, `redact_none`; здесь значение переопределяется).

- **[OQ-7] Модель хранения артефактов. РЕШЕНО (состав и принцип; имена файлов и
  порог размера настраиваются при реализации).** Один каталог на запуск плюс `Store`
  для крупного, своей базы нет:
  ```
  .runs/<run_id>/
    brief.md                      бриф как получен
    plan.v1.json, plan.v2.json    версии плана
    review.v1.json                замечания verifier (формат из OQ-5)
    approval.json                 хэш утверждённого плана, кто, когда
    trace.jsonl                   JsonlTelemetry
    checkpoints.db                SqliteCheckpointer
    store.db                      SqliteStore: выходы шагов выше порога
  ```
  - В каждую версию плана пишутся `inventory_digest` (`artifact_key` по снимку
    инвентаря), `engine_version` и `plan_hash`. Формат чекпойнта меняется между
    версиями (в коде есть поля «New in v0.7.0»), поэтому возобновление на другой
    версии движка отклоняется с понятной причиной, а не падает посреди шага.
  - Выход шага выше порога (порядка 32 КБ) лежит в `store.db`, в состоянии остаётся
    ссылка `{store_ref, size, sha256}`: чекпойнтер пишет состояние целиком на каждом
    шаге.
  - Отладочного `workflow.py` нет (кодген отвергнут); вместо него команда «показать
    план как граф».
  - Очистка по запросу пользователя и по возрасту, но не автоматически для
    утверждённых планов.
  - Ограничение: SQLite-файлы рассчитаны на режим одной машины, что совпадает с
    локальной архитектурой; переход на Postgres не меняет состав данных.

- **[OQ-8] Финальная схема `plan.json`. РЕШЕНО (состав полей, §6).** Закрыты поля
  входов (§6.1), прав (§6.2), `may_ask` (OQ-11), `final_outputs`, `run_limits`,
  `approval` с `plan_hash` (OQ-4), `verification` (OQ-5), `provenance` (OQ-7), итог
  запуска `completed | partial | failed`. Остаётся при реализации: файл JSON Schema и
  функция `validate_plan`.

- **[OQ-9] Проверка совместимости «план <-> бэкенд». РЕШЕНО.** Каталог и правила
  сверки: §6.2. Выбор агента в v1 только по имени (проверено: у Kiro и Claude Code
  есть, у Codex и LLM нет; MCP и skills SDK не передаёт).
  - Сопоставление «агент -> бэкенд» живёт в отдельном `inventory.json`, не в плане:
    бэкенд это свойство окружения, один утверждённый план должен запускаться на
    другой машине с другим набором агентов. Запись агента:
    `{"backend": "...", "agent": "<имя у бэкенда>", "permissions": [...]}`, где
    `permissions` перечисляет допустимые уровни прав (`read_only | allowlist | full`).
  - Цепочка проверки: план -> инвентарь -> каталог возможностей бэкенда (§6.2). Если
    агент доступен на нескольких бэкендах, в v1 берётся первый в списке `backends`
    (порядок задаёт пользователь), умного выбора нет.
  - План, который нельзя исполнить ни на одном доступном бэкенде, останавливается на
    проверке сборки ДО утверждения, с кодом ошибки по каждому шагу (например
    `permission full not allowed for backend claude in inventory`). Человек не
    утверждает заведомо неисполнимый план.

- **[OQ-10] Загрузка и развитие инвентаря. РЕШЕНО (имена каталогов и формат описаний
  агентов уточняются при реализации).**
  - В v1 инвентарь только читается. Источник: `inventory.json` либо каталог
    `.workflow/inventory/` с несколькими файлами, склеиваемыми по алфавиту; формат
    описан JSON Schema. `inventory_digest` = `artifact_key` от нормализованного
    содержимого.
  - Агент-проектировщик видит только имена, описания и допустимые права, не пути и не
    ключи.
  - Автосоздание недостающих агентов не делается. Если плану нужен отсутствующий
    агент, verifier ставит `blocker` с кодом `agent_missing` (добавляется в закрытый
    список кодов OQ-5), а предложение создать агента показывается человеку текстом.
    Модель, заводящая себе агентов с правами, нарушает границу безопасности OQ-4.
  - Развитие инвентаря только вручную. Изменение инвентаря меняет `inventory_digest`
    и делает недействительным утверждение уже одобренного плана (OQ-4): права не
    должны расти незаметно.

- **[OQ-11] Уточняющий вопрос как разрешённое поведение шага. РЕШЕНО.**
  - Объявляется в плане: поле шага `may_ask: {max_questions: 1}`, по умолчанию
    выключено. План проверяется до запуска, а человек при утверждении видит, какие
    шаги могут его побеспокоить.
  - Вопрос только МЕЖДУ шагами. Прерывание перезапускает узел с первой строки и
    весь параллельный фронт, поэтому вопрос посреди хода агента (особенно
    CLI-подпроцесса) не поддерживается. Задаёт его отдельный чистый узел перед
    шагом: шаг сперва возвращает структурированное «нужно уточнение» (вопрос,
    варианты) без побочных эффектов, исполнитель вызывает `ctx.interrupt` с
    `ClarificationRequest`, ответ добавляется во вход, шаг запускается заново.
  - Режим без человека: остановка с причиной (`stalled: needs_clarification`).
    Значение по умолчанию только если автор плана задал `default_answer` явно.
  - Ответ входит в ключ кеша шага (он меняет вход). Вопрос и ответ пишутся в
    трассировку отдельным событием `clarification`.
  - Превышение `max_questions` роняет шаг с понятной причиной.
  - Принятая цена: шаг, которому понадобилось уточнение на 80% работы, либо
    завершается, либо теряет работу.
  - После остановки `needs_clarification` (авто-режим без `default_answer`) человеку
    доступны два действия: (1) ответить и начать НОВЫЙ запуск того же плана с этим
    ответом как параметром запуска; выполненные шаги не повторяются, их результаты
    берутся из кеша по ключу содержимого; ответ не меняет план, поэтому утверждение
    остаётся в силе (тот же `plan_hash`); (2) отменить запуск. Продолжить тот же запуск
    нельзя: провал задачи `ask` уже зафиксирован в чекпойнте, а завершённая задача
    считается выполненной. Задание `default_answer` в плане меняет `plan_hash` и
    требует повторного утверждения: это путь «отклонить с замечанием», а не кнопка на
    экране остановки.
  - Условие: путь (1) работает, только если исполнитель кеширует результаты шагов
    (`skip_if_done` по ключу содержимого, см. `step_cache_key`). `add_plan_executor`
    сам этого не делает, кеш подключается в сборщике; без него новый запуск повторит
    всю работу.
  - Проверено спайком `spikes/clarification_spike.py` (память и SQLite):
    - двухфазная схема даёт 2 вызова агента; вариант «прерывание внутри обработчика
      шага» повторяет пробный вызов при возобновлении и даёт 3;
    - тело `ask` выполняется дважды (первый раз и при повторе после ответа), поэтому
      оно обязано быть чистым;
    - задача с побочным эффектом, которую планировщик добавил в том же вызове, что и
      `ask`, повторяется при возобновлении (2 запуска); если её поставить после
      повторного шага (`prerequisites=(s1#2,)`), запуск один. Ранее объявленные
      задачи в раунд `ask` попасть не могут: `ask` появляется только когда план
      простаивает. Правило для сборщика: всё, что планировщик добавляет вместе с
      `ask`, должно зависеть от повторного шага;
    - ответ входит в вход шага, поэтому ключ содержимого повторного запуска
      отличается от первого и зависит от ответа; одинаковый ответ даёт одинаковый ключ;
    - без человека: без `default_answer` запуск останавливается с причиной
      `needs_clarification` и без прерывания, с ним продолжается; ответ вне `options`
      и превышение `max_questions` дают отказ с понятной причиной.

### Отложенные (сознательно вне v1)

- **[OQ-D1] Save/load черновика посреди петли design⇄verify.** В v1 только
  утверждённый план. Нюанс (из ревью): если design-фаза исполняется как граф
  с чекпойнтером, черновики и состояние петли сохраняются САМИ. Тогда «не в v1»
  — осознанное решение НЕ использовать это (хранить/чистить/редактировать
  секреты), а не отсутствие механизма.

- **[OQ-D2] UI.** Следующий этап. В v1 — программный интерфейс или CLI.

- **[OQ-D3] Заметки шага (память, переживающая перезапуск).** Решено не делать в v1;
  вместо канала заметок следующая попытка шага получает обратную связь проверок.
  Причины: второй системе памяти рядом с первой нужны отдельные правила, а заметки
  ломают кеш (либо входят в ключ и кеш почти перестаёт работать, либо справочные и
  тогда почти бесполезны). Если пересматривать, то с условиями: `Store` с
  пространством `("workflow", plan_id, step_id, "notes")` (локально `SqliteStore`);
  запись и чтение только через хендлер исполнителя; в следующую попытку того же
  шага попадают, в потомки только по явной привязке (OQ-8); в `checks` не
  участвуют никогда; лимит размера, очистка вместе с планом, редакция секретов
  включена по умолчанию. Пересмотр на реальном случае.

## 8. Отдельная задача (НЕ часть этого модуля): KiroBackend на Windows

Независимый фикс. Диагностика и дизайн правки проведены в этой сессии; реализацию
пользователь передаёт в Claude.

**Статус: реализовано (вариант A), закоммичено.** `close()` эскалирует через
`_terminate()` → `_kill()`; пять новых тестов в `tests/test_kiro_backend.py`
(ветка без POSIX-сигналов, группа процессов, исчезнувшая группа, повторный
`close()`, уже завершившийся процесс). Windows-тест проверен «от противного»: на
старом коде он падает именно с `AttributeError: module 'signal' has no attribute
'SIGKILL'`. Не проверено на настоящей Windows-машине. Вариант B (`taskkill /T` или
Job Object) остаётся отдельной задачей.

**Файл:** `agentflow/backends/kiro.py`

**Корень проблемы:** код завязан на числовые сигналы (`signal.SIGKILL`/`SIGTERM`)
как на «уровень жёсткости» завершения — это непортируемо.

1. `close()` (~строка 163): обращение к `signal.SIGKILL` вычисляется ДО вызова
   функции и не обёрнуто в suppress → на Windows (где нет `signal.SIGKILL`) летит
   `AttributeError` прямо при закрытии. Это и есть симптом из брифа.
2. `_signal_group()` fallback: снова читает `signal.SIGKILL` вне `suppress` — упал
   бы и здесь.

**Предложенный фикс (заменить абстракцию, а не точечно):** ввести две операции
по смыслу, а не по сигналу:
- `_terminate(proc)` — мягко: POSIX → `SIGTERM` группе; Windows → `proc.terminate()`;
- `_kill(proc)` — жёстко: POSIX → `SIGKILL` группе; Windows → `proc.kill()`.

Тогда `close()` — эскалация по смыслу (stdin close → wait → terminate → wait → kill),
без непортируемого чтения атрибутов ни на одной платформе.

**Требования брифа к фиксу + статус:**
- POSIX: группа процессов, эскалация SIGTERM→SIGKILL — логика есть, перенести на операции.
- Windows: платформенная остановка с ожиданием и форс при таймауте — через ту же эскалацию.
- Безопасный повторный `close()` + «процесс уже завершился» — проверить и закрепить тестом.
- Проверка завершения ДОЧЕРНИХ процессов — открытая развилка (ниже).
- Регрессионные тесты: обычное закрытие и таймаут. Текущий
  `test_close_terminates_then_kills_on_timeout` проверяет только POSIX-путь;
  нужен тест Windows-ветки (эмуляция отсутствия `os.getpgid`/`signal.SIGKILL`).

**Развилка по реапингу дочерних на Windows (`kiro-cli-chat` переживает kill родителя):**
- Вариант A (минимальный): `terminate()` → `kill()`. Чинит `AttributeError`, но не
  гарантирует смерть внука. Рекомендация для v1 + TODO.
- Вариант B (полный): `taskkill /F /T /PID` или Job Object при старте. Надёжнее,
  но больше кода и внешняя зависимость.

Рекомендация: A в v1 с явным комментарием-ограничением, B — отдельной задачей.

**Поправка из ревью (эскалация на Windows бессмысленна).** На Windows
`proc.terminate()` — это уже жёсткое завершение (`TerminateProcess`), поэтому
последовательность `terminate() → kill()` на Windows вырождается: мягкого шага
там нет. Настоящая мягкая остановка требует запуска с `CREATE_NEW_PROCESS_GROUP`
и посылки `CTRL_BREAK`. Для v1 это, вероятно, избыточно — достаточно одного
жёсткого завершения на Windows, но это надо зафиксировать как сознательный выбор,
а не как «эскалацию, которой нет».

**Непроверенное предположение (из ревью, не подтверждал).** `claude` и `codex`
на Windows npm ставит как `.cmd`, и `create_subprocess_exec("claude")` такой файл
может не найти. Касается claude_code/codex-бэкендов, не KiroBackend. Требует
отдельной проверки на Windows-машине.

## 9. Справочное сравнение с Kiro Workflows

Архитектурно полезно разделять создателя графа и исполнителей его шагов:
агент, планирующий реализацию внутри ноды, не является создателем окружающего
workflow.

В приведённом пользователем ответе конкретной сессии Kiro создатель графа
назывался `workflow-creator`; отдельный агент семантической проверки плана
в доступном ему наборе не упоминался. Это свидетельство о той сессии, а не
доказательство отсутствия всех внутренних проверок во всём продукте. Названия
и доступный набор могут зависеть от версии. Исполнение Kiro в рамках этого
сравнения не проверялось.

Для нашего дизайна `wf-verifier` сохраняется в первой версии: ограниченный цикл
design/verify входит в согласованный сценарий. Валидация схемы и человеческое
утверждение не заменяют проверку полноты, допущений и проверяемости плана.
Пары исполнителя и проверщика результатов — отдельный уровень исполнения;
заявления об их сравнительной ценности не считаются измеренными результатами.
